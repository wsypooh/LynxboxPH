# LynxboxPH

Property/tenant/invoice management system. Two apps in this repo:

- `api/` — AWS Lambda API (Serverless Framework, Node/TypeScript), single DynamoDB table
- `lynxbox-ph/` — Next.js 14 frontend (Chakra UI, react-hook-form + zod)

## ⚠️ Two separate route configs — both must be updated for a new endpoint

- `api/serverless.yml` is **local-dev only** (drives `serverless-offline` and the Express `local-server.ts` wrapper used by `npm run dev`). Editing it has **zero effect** on any deployed environment (sandbox/prod).
- `infra/modules/api/routes.tf` is the **actual deployed** API Gateway config (Terraform, applied via `infra/scripts/deploy-infra.ps1` → `terraform apply`). This is the one real environments read.

Whenever you add a new Lambda handler/route, add it to **both**:
1. `api/serverless.yml` — an `- http:` block (see pattern below), for local dev.
2. `infra/modules/api/routes.tf` — an `aws_apigatewayv2_route` block with `authorization_type = "JWT"` and `authorizer_id = aws_apigatewayv2_authorizer.cognito.id`, for it to work anywhere real.
3. `api/local-server.ts` — also needs an explicit `app.all('/api/...', ...)` registration (see Backend section below); it's a third, separate route list.

If a route is missing from `routes.tf`, it falls through to `$default`, which has no authorizer attached — `event.requestContext.authorizer?.claims` comes back null, every handler's `resolveActor()` returns null, and you get a 401 that never even reaches your handler's own code (check CloudWatch for the handler's console output to confirm Lambda wasn't invoked at all, before assuming it's an app bug). A route deployed with the JWT authorizer correctly still rejects unauthenticated/expired tokens the same way — the giveaway that it's a missing-route problem rather than a bad-token problem is that *other* endpoints using the same token succeed while this one alone 401s.

## Infrastructure (`infra/`)

Terraform. Environment-specific values (`domain_name`, etc.) live in `infra/environments/{dev,prod}.tfvars`, not defaults in `variables.tf` — running a bare `terraform plan`/`apply` without `-var-file=environments/dev.tfvars` (or `prod.tfvars`) interactively prompts for every required variable one at a time instead of failing fast. Prefer `infra/scripts/deploy-infra.ps1 -Environment dev` (or `prod`), which resolves the right var-file automatically; if running Terraform directly, always pass `-var-file` explicitly.

**Lambda code deploys are separate from `terraform apply` and easy to forget.** The `aws_lambda_function` resource has `lifecycle { ignore_changes = [filename, source_code_hash, environment] }` — Terraform only ever creates the initial placeholder function and manages the IAM/routes/env-var *definitions* around it, never the live code or env vars. Every backend code change (new handler, bug fix, anything in `api/src/`) needs `infra/scripts/deploy-lambda.ps1 -Environment dev` to actually reach a deployed environment; `terraform apply` alone will not push it, and there's no error to tell you it didn't.

If a resource already exists in AWS outside Terraform's state (e.g. created by hand in the console before an `apply`), `terraform import` it rather than deleting and letting Terraform recreate it — recreating loses whatever state the manual resource already had (e.g. Cognito group memberships) for zero benefit once imported.

## Backend (`api/`)

**Single-table DynamoDB design.** One table (`process.env.DYNAMODB_TABLE`, default `lynxbox-ph-dev`), one GSI (`GSI1`). Entity types declared in `api/src/lib/dynamodb.ts` (`EntityType` enum) — this is the only place entity types are registered. `ddbDocClient` is exported from there too.

**Models** (`api/src/models/*.ts`): interface extends `BaseEntity`, adds `[key: string]: any` (lets the generic repo `update()` iterate fields), plus a hand-written `XInput` type and a factory `createX(data: XInput, code): X` using `uuidv4()` + `new Date().toISOString()`. The factory builds `PK`/`SK`/`GSI1PK`/`GSI1SK` explicitly as template strings, e.g. `PK: 'INVOICE#'+id`, `GSI1PK: 'TENANT#'+tenantId`, `GSI1SK: 'INVOICE#'+billingMonth+'#'+id` (GSI1 = "list by parent, sorted/filtered by a natural key").

**Repositories** (`api/src/repositories/*Repository.ts`): static-method classes, own `TABLE_NAME` const. Every repo has an identical dynamic `update()` builder (iterates `Object.entries(updates)`, skips key/meta fields, builds `#name`/`:value` maps, always bumps `updatedAt`, `ReturnValues: 'ALL_NEW'` — copy this verbatim for new repos). Soft delete = `update(id, { deletedAt: now })`. Listing "by parent" = `QueryCommand` on GSI1 with `begins_with(GSI1SK, prefix)`. No batch/transaction commands anywhere — parallelism is `Promise.all` over per-item Get/Put/Update/Query, aggregation/filtering happens in JS after the fetch.

**Handlers** (`api/src/handlers/*/handler.ts`): static-method classes. `handle()` starts with `const actor = await resolveActor(event); if (!actor) return ApiResponse.unauthorized(...)` (`api/src/lib/auth.ts` — the single shared source of the caller's identity/role, replacing the old per-file `getUserId(event)` helper) plus a per-file `getXId(event)` (regex on `event.path`, not `pathParameters`). `handle()` is an if/else-if dispatcher ordered **most-specific path first** (sub-paths like `.../payments` before the generic `/{id}` routes; the generic GET explicitly excludes the bare list path), with a `canWrite(actor)`/`canDestroy(actor)` check (→ `ApiResponse.forbidden(...)`) guarding each write/destructive branch. All responses go through `ApiResponse.success/error/notFound/unauthorized/forbidden` (`api/src/lib/apiResponse.ts`). Ownership check is always `if (!x || x.ownerId !== actor.accountId || x.deletedAt) return ApiResponse.notFound(...)` — see RBAC section below for what `accountId` means when a handler is called by someone other than the account owner.

**`api/src/index.ts`** routes by `event.path?.includes(...)` string checks (not path params), most-specific first, falling through to `propertyHandler` last.

**`api/serverless.yml`**: one `- http:` block per method+path, `cors: true` + `authorizer: { name: ApiGatewayAuthorizer, type: request }` on every protected route (public routes under `/api/public/*` and `/api/signup` omit the authorizer). IAM already grants generic `dynamodb:{Query,Scan,GetItem,PutItem,UpdateItem,DeleteItem}` on `Resource: "*"` — new entity types need no IAM change. Local-dev only — see the callout at the top of this file.

**`api/local-server.ts`**: the actual thing `npm run dev` runs (`ts-node-dev` over this file, which imports the compiled `./dist/index`). It's a hand-rolled Express wrapper that explicitly registers every route with `app.all('/api/...', ...)` — there's no wildcard/proxy matching, so a new route needs its own `app.all(...)` line here too, or it 404s locally even though the Lambda handler code is correct.

**`infra/modules/api/routes.tf`**: the real, deployed API Gateway routes (Terraform). One `aws_apigatewayv2_route` block per method+path, `authorization_type = "JWT"` + `authorizer_id = aws_apigatewayv2_authorizer.cognito.id` on every protected route. Applied via `infra/scripts/deploy-infra.ps1` (needs a live AWS SSO session) → `terraform plan`/`apply`. See the callout at the top of this file — this is the file that actually matters for sandbox/prod.

## Ledger System

Tenant charges and payments live in a separate ledger (`ChargeEntry` / `PaymentEntry` in `api/src/models/ledgerEntry.ts`, `LedgerRepository`), not on the `Invoice` record directly. Full design, every deviation from the original plan, and current status are in `docs/Ledger-Plan.md` — read that before touching penalty or payment logic; it's kept up to date, not just a historical spec.

Quick orientation:
- **FIFO payment application**: `LedgerRepository.recordPaymentWithFIFO` always settles the oldest unpaid `ChargeEntry` first, penalty before principal, using `penaltyPaid` to avoid re-billing already-collected penalty (simple interest on the *remaining* principal, not the original amount — see the doc if this looks like it's undercharging, it's usually by design).
- **Void, not delete, for non-draft invoices**: `InvoiceHandler.deleteInvoice` only works on `draft`; anything else goes through `POST /api/invoices/{id}/void`, which soft-deletes the linked `ChargeEntry` but keeps the invoice record and its number (avoids invoice-number reuse, preserves audit trail).
- **Two payment views on an invoice are intentionally different, not duplicates**: `ledgerPayments` (what actually settled *this invoice's own* charge — often empty, since FIFO pays the oldest charge first) vs `paymentsReceived` (everything received since the tenant's *previous* invoice, regardless of which charge it hit — this is the one shown on the customer-facing Statement of Account / PDF).

## Documents Feature

Buildings and tenants can each have `Document` records (SEC certs, business permits, lease PDFs, government IDs) attached, uploaded direct-to-S3 via presigned URL. Full design and the decisions behind it are in `docs/Documents-Feature-Plan.md` — read that before touching upload/S3-key logic; it's kept up to date, including the deviations noted below, not just a historical spec.

Quick orientation:
- **S3 key is a UUID, never the original filename.** `S3Service.getPresignedUploadUrl` names the object `<folderPrefix>/<uuid>.<ext>` to avoid collisions/unsafe characters — the human-readable name only ever lives in `Document.fileName`. To make downloads/previews still show the original name, `S3Service.getPresignedViewUrl(key, expiresIn, downloadFileName?)` signs a `ResponseContentDisposition` header (built by `buildContentDisposition()`) into the URL whenever a filename is passed — `DocumentHandler.getViewUrl` always passes `document.fileName`. If you add another S3-key-based download path, pass the filename through the same way or you'll get UUID-named downloads.
- **Row actions are icon buttons, not text buttons**, across `DocumentList`/`TenantList`/`InvoiceList`/buildings page: `FiEye` (view), `FiEdit2` (edit), `FiTrash2` (delete), `FiSlash` (void, kept visually distinct from delete). `DocumentList` has its own `DocumentEditModal` for post-upload edits (category/expiryDate/notes via `PUT /api/documents/{id}`) — this wasn't in the original plan's UI section, added afterward since notes/category are otherwise only ever set once, at upload time.
- **`TenantContract.id`** is generated client-side the moment a new contract row is added in `TenantForm.tsx`, using `crypto.randomUUID()` (the frontend has no `uuid` package dependency — don't add one, this is the established pattern). Legacy contract rows saved before this feature existed have no `id` and simply can't have a document attached — that's intentional, not a bug to fix by retrofitting an id on read. `useFieldArray` in `TenantForm.tsx` uses `keyName: '_key'` specifically to stop React Hook Form's own internal row key from colliding with this domain `id` field.
- Document's own frontend types live in `features/documents/types.ts` (not `features/invoicing/types.ts`) since documents aren't part of the invoicing domain — mirror this split for any future non-invoicing entity.

## Role-Based Access Control (RBAC)

Per-account roles (`owner`/`manager`/`staff`/`viewer`) plus a separate platform-admin role for cross-account, read-only visibility. Full design, every deviation from the original plan, and current status are in `docs/RBAC-Admin-Plan.md` — read that before touching `api/src/lib/auth.ts`, membership, or invite logic; it's kept up to date, not just a historical spec.

Quick orientation:
- **Two separate mechanisms, not one.** Platform-admin is a **Cognito Group** (`platform-admin`) read from JWT claims — coarse, rare, a change needs logout/token-refresh to apply. Per-account role is a **DynamoDB `MEMBER#` record** (`api/src/repositories/membershipRepository.ts`), read fresh by `resolveActor()` on every request — a role change applies on the very next call. Don't move per-account roles into Cognito Groups; Groups can't represent "manager on account A, viewer on account B," which is a real supported case (one Cognito user can belong to multiple accounts).
- `resolveActor(event)` (async) in `api/src/lib/auth.ts` is the single source of truth for `{ sub, accountId, role, isPlatformAdmin, displayName, email }`. `accountId` is the sub for a solo account (no `MEMBER#` rows exist — zero migration needed for existing accounts) or the account they're currently acting in otherwise, resolved via the `X-Account-Id` header and validated against real memberships. Gate writes with `canWrite(actor)`, destructive actions with `canDestroy(actor)`, member management with `canManageMembers(actor)`.
- **Invites create real Cognito users** via `AdminCreateUser`/`AdminGetUser` (`api/src/lib/cognitoAdmin.ts`), with a generated temporary password emailed through ZeptoMail (Cognito's own invite email is suppressed) — needs `USER_POOL_ID` set and `cognito-idp:{AdminCreateUser,AdminGetUser,DescribeUserPool}` IAM permission on whatever credentials are calling it. The deployed Lambda role has this via Terraform; **local dev needs `USER_POOL_ID` added to `api/.env` by hand** (it's not there by default) plus those Cognito admin actions granted to whatever AWS credentials `api/.env` uses — the deployed Lambda's IAM role is irrelevant locally.
- **`api/local-server.ts`'s mock JWT-claims object must stay in sync with whatever claims real handlers read.** It only forwards `sub`/`cognito:username`/`email`/`name`/`cognito:groups` from the decoded token today — if a future feature reads another claim (e.g. a new custom attribute), add it here too or local testing will silently behave as if that claim is always absent, even though the real deployed API Gateway authorizer passes it through fine.
- **Multi-valued claims (e.g. `cognito:groups`) arrive at a handler via `event.requestContext.authorizer.claims` as a bracket-wrapped, comma-separated, *unquoted* string** — e.g. `"[platform-admin]"` or `"[group-a, group-b]"` — confirmed via CloudWatch on the real deployed API, not JSON and not a plain comma-joined string (both were tried and wrong first). See `parseGroups()` in `api/src/lib/auth.ts` for the regex-based parse. **This class of bug can't be caught locally** — `local-server.ts`'s mock passes through the real decoded-JWT array untouched, so anything touching this exact serialization format only fails once actually deployed; treat any new multi-valued-claim consumer as needing a real sandbox test, not just local + `tsc`.

## Pricing & Plan Limits

Free/Starter/Growth/Business tiers gate active property listings, invoices/month, team seats, and document storage. Full design, every deviation from the original plan, and current status are in `docs/Pricing-Strategy-Plan.md` — read that before touching plan limits, enforcement, or the platform-admin plan-toggle endpoint; it's kept up to date, not just a historical spec.

Quick orientation:
- **`Property` (the public listing entity) and `Building`→`Tenant`→`Invoice` (the back-office pillar) are two separate things — pricing gates the former, not the latter.** `Property` (`api/src/models/property.ts`) is a standalone, publicly-browsable listing (title/price/photos/location, its own `/api/public/properties` API), unrelated to any Building/Tenant record — it's the product's marketing/vacancy-advertising pillar, not legacy dead code. Tiers gate `Property` listing count plus a monthly invoice fair-use cap, deliberately **not** Building/Tenant count.
- **Plan lives on a new `EntityType.ACCOUNT` row** (`PK: ACCOUNT#<accountId>`, `SK: PLAN#<accountId>`), read via `AccountRepository.getPlan()` and attached to every request as `actor.plan` in `resolveActor()` — one extra `Get` per request, same pattern as every other per-request lookup there. No row = defaults to `'free'` (same zero-migration lazy-default convention RBAC uses for solo accounts with no `MEMBER#` rows).
- **`api/src/lib/planLimits.ts`'s `PLAN_LIMITS` is the only place tier limits are registered** — hardcoded on purpose, no admin-editable settings table. Every enforcement check imports from there.
- **The monthly invoice quota counts by creation date, not `billingMonth`** — a separate `USAGE#<accountId>#<YYYY-MM>` row under the same `ACCOUNT#` PK, incremented via a fire-and-forget `AccountRepository.incrementMonthlyInvoiceCount()` call (a counter-write failure must never fail an already-created invoice). It's a soft cap: only hard-blocks once a full calendar month has passed still over the limit, checked against the one prior month, not a rolling window.
- **Listing visibility duration and search placement are computed at read time, never via a cron job.** `Property.expiresAt` (set from the plan at creation; `null` = never expires) is only checked in `PropertyRepository`'s public-facing query methods — an owner's own private listing view always shows everything, expired or not, renewable via `PUT /api/properties/{id}` with `renew: true` (no separate route). Search placement (`standard`/`priority`/`featured`) is derived from the owner's *current* plan at request time in `PropertyHandler.sortByPlacement()`, and only reorders the *default* browse order — an explicit `sortBy` from the caller is left alone.
- **Downgrading unlists the oldest excess listings, never deletes them.** `reconcilePropertyListingsForPlan()` (`api/src/lib/reconcilePropertyListings.ts`) flips `Property.status` to `'unlisted'` (distinct from soft-delete). It's a standalone function on purpose — the (separate, later) Payments and Subscription plan's cron job reuses this exact function for its own past-due-revert-to-Free case.
- **Setting a plan is platform-admin-only** (`PUT /api/platform-admin/accounts/{accountId}/plan`, surfaced on the platform-admin account detail page) — there's no self-serve endpoint because there's no payment gate yet; an owner could otherwise grant themselves Business for free. This is platform-admin's first write action, a narrow exception to the read-only stance in `docs/RBAC-Admin-Plan.md` (see that doc's decision #1).
- **Billing/payment processor integration is a separate, later plan** (`docs/Payments-and-Subscription-Plan.md`, not yet implemented) — don't build a "Request Upgrade"/checkout flow against this scope, it would just be thrown away.

## Frontend (`lynxbox-ph/`)

**Services** (`src/services/*Service.ts`): singleton class instance exported at the bottom. Private `request<T>()` wraps `fetch`, attaches auth headers via `getAuthHeaders()`, and unwraps the API's `{ success, data }` envelope to just `data`. Each public method calls `request<{ x: T }>(...)` and returns `res.x`.

**Components**: Chakra UI throughout. One `useDisclosure()` per modal. CSV import components (see `TenantCsvUpload.tsx`) follow: module-level `CSV_HEADERS`/`EXAMPLE_ROW`, hand-rolled `parseCSV`, a `validateRow()` pure function producing `{ rowNum, data, errors, payload }`, template download via Blob + synthetic `<a>` click, sequential (not `Promise.all`) import loop with a progress bar, toast summary at the end. `PaymentModal` (`features/invoicing/components/PaymentModal.tsx`) is generic/reusable — just `amount`/`date`/`paymentMethod`/`note` — wire it to any `onSubmit` rather than writing a new payment form.

**List rows/tables**: row-level actions (`TenantList`, `InvoiceList`, `DocumentList`, building cards) are icon-only `IconButton`s (`react-icons/fi`) wrapped in a Chakra `Tooltip` with a short label, not text buttons — match this for any new action rather than adding a labeled `Button`. In `TenantList`/`InvoiceList`, the whole `<Tr>` is clickable (`cursor="pointer"`, `onClick` navigates to the record's view page) and the checkbox/Actions `<Td>` calls `e.stopPropagation()` so per-row controls don't also trigger navigation — follow the same pair (row `onClick` + `stopPropagation` on interactive cells) for any new clickable list.

**Types**: `src/features/invoicing/types.ts` is the single frontend contract-types file; new domain types go here.

**Static export** (`next.config.js` sets `output: 'export'`): every dynamic route (`app/**/[param]/page.tsx`) needs `generateStaticParams()`, which cannot be exported from a `'use client'` file. Split into a thin server `page.tsx` (no `'use client'`, exports `generateStaticParams()` returning a single placeholder like `[{ id: '_' }]`, renders a client component passing the param as a prop) plus the actual `'use client'` `XyzClient.tsx` doing the real work — see `dashboard/tenants/[id]`, `dashboard/invoices/[id]`, `dashboard/platform-admin/accounts/[accountId]` for the pattern. `tsc --noEmit` and `next lint` both pass even when this is violated — only a real `next build` catches it.
