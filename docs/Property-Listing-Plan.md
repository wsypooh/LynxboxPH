# Property Listing — Plan

Status: **implemented**. This doc is kept up to date, not just a historical spec — see each section's own notes for what changed and any tradeoffs accepted along the way. Read this before touching property image upload or the public property endpoints.

## Context

`Property` (`api/src/models/property.ts`) is the public, publicly-browsable marketplace listing entity — title/price/photos/location, its own `/api/public/properties` API — described in `CLAUDE.md`'s Pricing & Plan Limits section as the product's marketing/vacancy-advertising pillar, separate from Building/Tenant/Invoice. This doc covers a series of problems found and fixed while working through this feature: how property images actually get from the browser to S3, how the public listing endpoints exposed owners' phone/email to scraping, several property form/field UX bugs, a human-friendly `propertyNumber`, and a listing-visibility enforcement gap across the public endpoints.

## Image upload — direct-to-S3, not base64-through-Lambda

### What was found

- `PropertyForm.tsx` converted every selected image to base64 and embedded it in the create/update JSON body, sent through API Gateway → Lambda. For many/large photos this risks API Gateway's payload limit plus the ~33% base64 size inflation — the same tradeoff `docs/Documents-Feature-Plan.md` weighed when it chose presigned-URL upload for documents instead of copying this pattern.
- Presigned-URL scaffolding already existed in the code (`S3Service.getPresignedUploadUrl`, `PropertyHandler.getPresignedUploadUrl`, `propertyService.uploadPropertyImage`) but had **zero callers** — unused scaffolding, exactly as `Documents-Feature-Plan.md` had already noted when it was written. It also had a latent bug: `propertyService`'s presigned-upload helpers never unwrapped the API's `{ success, data }` response envelope, so `uploadUrl`/`key` would have come back `undefined` the moment something actually called it.
- Further dead code existed alongside the live base64 path: `PropertyHandler.handleMultipartPropertyCreation`, `handleBase64Images`, and a second, separate legacy multipart endpoint `POST /api/properties/{id}/images` (`PropertyHandler.uploadPropertyImage`). Confirmed via grep across both `api/` and `lynxbox-ph/` — no live caller anywhere for any of these.
- `PropertyHandler.getPresignedUploadUrl` required the target property to already exist in DynamoDB (`PropertyRepository.findById` 404s if not found) — which blocks the one case that matters most: a **brand-new** listing has no id yet at the point its first photos are being picked.
- Property images get server-side watermarking + resizing by default (`ImageProcessingService.processForPropertyUpload`, gated by `WATERMARK_ENABLED` which defaults to on) inside the old base64 path's `S3Service.uploadImage()`. Naively switching to a raw presigned PUT would have silently dropped this — the file bytes go straight from the browser to S3 and never touch Lambda, so there's no point left in the old flow where processing could happen.

### What changed

- The client now generates the property's id **upfront**, client-side (`crypto.randomUUID()` — same established pattern as `TenantContract.id`, no new `uuid` frontend dependency), the moment the create/edit form mounts, and reuses it for the form's whole lifetime. This is what makes uploading before the property record exists possible at all.
- Upload is now a 3-step flow per image (mirrors Documents' presigned pattern, with one extra step Documents doesn't need):
  1. `GET /api/properties/{id}/images/upload-url` — returns a presigned S3 PUT URL + key. No longer requires the property to already exist; ownership is only checked when it does (a new listing can't be ownership-checked against a record that doesn't exist yet — same accepted-risk shape as Documents' "orphaned S3 object is not a data-integrity problem" reasoning).
  2. Browser `PUT`s the raw file bytes straight to S3 — bypasses API Gateway/Lambda entirely.
  3. **`POST /api/properties/{id}/images/confirm`** (new) — downloads that one just-uploaded object back out of S3, runs it through the same watermark/resize pipeline the old base64 path used (`S3Service.processUploadedImage`, wrapping `ImageProcessingService.processForPropertyUpload`), and overwrites it in place. This is the step Documents never needed (it doesn't process uploaded files at all) — it's what lets watermarking keep working while the raw bytes still never pass through API Gateway's request/response body.
  4. `POST`/`PUT /api/properties` (create/update) now just take `images: string[]` — plain, already-uploaded S3 keys. No `base64Images` anywhere anymore, front or back end.
- Deleted as dead code: `handleMultipartPropertyCreation`, `handleBase64Images`, the legacy `uploadPropertyImage` handler, and its `POST /api/properties/{id}/images` route in all three route-config files (see `CLAUDE.md`'s callout on why all three — `serverless.yml`, `infra/modules/api/routes.tf`, `local-server.ts` — always need to move together).
- `PropertyForm.tsx`'s image state was refactored from three separately-tracked arrays (`selectedImages: File[]`, `imagePreviews: string[]`, `removedImages: string[]`) into one `ImageItem[]` (`{ kind: 'existing'; key } | { kind: 'new'; file; previewUrl }`), using synchronous `URL.createObjectURL()` previews instead of async `FileReader.readAsDataURL()`. This wasn't just cleanup: the old code's `removeImage` decided "is this a new or existing image?" by comparing the clicked index against `selectedImages.length`, silently assuming new images sit at the *front* of `imagePreviews` — but they're actually appended at the *end*. In edit mode, with existing images already loaded, removing a newly-added image could misclassify it as existing (pushing its data-URL into the field meant for S3 keys to delete) while leaving the actual `File` untouched in `selectedImages` — so the "removed" image would silently reappear in the saved property. Discriminating by the item's own tagged `kind` instead of position removes the whole bug class.
- The upload-progress bar in `PropertyForm.tsx` existed in the JSX before this change but nothing ever called `setUploadProgress` with a real value — it's now wired to real per-file XHR progress during step 2 of the upload above.

### Accepted limitation

`getPresignedUploadUrl` and `confirmImageUpload` both skip ownership verification when the target property id doesn't exist yet in DynamoDB — there's nothing to check ownership against. Worst case, an authenticated user could cause a watermarked, orphaned image to sit under an S3 key prefix they don't otherwise control, never linked to any real property unless they go on to actually complete the create call themselves. Same risk shape Documents already accepted for its own orphaned-object case.

## Public listing contact-info scraping protection

### What was found

`GET /api/public/properties/{id}` — and, worse, the bulk `GET /api/public/properties` and `GET /api/public/search` — returned the **entire** `Property` record verbatim to any unauthenticated caller, including the real `contactInfo.phone` and `contactInfo.email` in plaintext JSON. This is scrapeable directly via the API with no need to even render the page (`view-source` was never the real threat model here), and the bulk list/search endpoints let a scraper harvest every listing's contact info in one paginated sweep rather than one at a time.

### What changed

- **`api/src/lib/contactMasking.ts`** (new) — `maskPhone`, `maskEmail`, `maskContactInfo`. Phone keeps the first 3 and last 2 digits, masking everything else in between while leaving existing separators/formatting alone (e.g. `+63 917 123 4567` → `+63 9** *** **67`). Email keeps the first character of the local part plus the full domain (`john.doe@example.com` → `j*******@example.com`) — domain stays visible so a masked listing still reads as a legitimate business address.
- Applied in `getPublicProperty`, `listPublicProperties`, and `searchPublicProperties` — these now only ever return the masked form. The owner-scoped, authenticated equivalents (`getProperty`, `listProperties`, `searchProperties`) are untouched — an owner viewing their own listings still sees their own real contact info.
- New **`GET /api/public/properties/{id}/contact`** (no auth) hands back the real `{ phone, email }`, but only for one listing at a time — never bundled into a list.
- Frontend (`PropertyDetailClient.tsx`): "Call Now" / "Send Email" are themselves the reveal action — clicking either fetches the real contact info (if not already fetched this visit), immediately opens `tel:`/`mailto:` with the real value, and swaps the sidebar's masked phone/email display for the real one. The fetched result is cached in component state so a second click on either button doesn't hit the API again.

### Decision made & accepted limitation

Chose **click-to-reveal with no login required**, over gating the reveal endpoint behind authentication or replacing direct contact entirely with a server-relayed inquiry form — this keeps the anonymous-visitor lead funnel frictionless, at the cost of weaker protection than the other two options would have given.

**No rate limiting on the reveal endpoint** — this repo has no rate-limiting infrastructure anywhere yet (no API Gateway usage plans, no per-IP throttling layer), so this wasn't added just for this endpoint. A scripted scraper can still work around the split by calling `/contact` once per known listing id; this raises the cost of scraping (N calls instead of 1, each yielding only one listing instead of a whole page) but does not make it impossible for a determined actor. If this turns out to matter in practice, the two follow-up options are: gate `/contact` behind login (real friction, but loses anonymous leads — the tradeoff this decision explicitly avoided), or add IP-based throttling (new infrastructure for this repo, not a small add).

## Property form field fixes (Area, Floor, Location)

### Area — decimal input was silently blocked

**What was found:** the Area (m²) `NumberInput` fed `parseFloat(value) || 0` straight back into its own controlled `value` prop on every keystroke. Typing `12.` parses to the number `12` (no decimal marker), which then re-renders the input — with `precision={2}` set — as `12.00`, wiping the decimal point before a digit after it could ever be typed. The up/down steppers worked fine (they never pass through that half-typed intermediate string), which was the tell that this was a controlled-input formatting fight, not a validation limit — the zod schema (`area: z.number().min(0, ...)`) never restricted decimals in the first place.

**What changed:** the field's displayed text is now tracked in its own `areaInputValue` state, decoupled from the numeric value hand fed to react-hook-form — `NumberInput`'s `value` prop follows `areaInputValue` (exactly what Chakra reports back, unmodified) while `onChange` separately parses and forwards a number to the form. This is the standard fix for this class of Chakra `NumberInput` bug: never feed a re-derived/reformatted number back in as the controlled value while the user is mid-keystroke.

### Floor — relabeled to mean "which floor", not floor count

**What was found:** the field was labeled "Floors" and read like a count of how many floors the building has, when what it actually means for a single listing is which floor level the unit is on.

**What changed:** relabeled to "Floor" in `PropertyForm.tsx`, with helper text ("Which floor the property is on (0 = ground floor)") clarifying the meaning — no schema or validation change, `features.floors` is still a plain non-negative number under the hood. Display everywhere it's shown now goes through a new `formatFloor()` helper (`lynxbox-ph/src/lib/utils.ts`): `0` → "Ground", `1` → "1st", `2` → "2nd", `3` → "3rd", `4`+ → "4th" etc., with the 11th/12th/13th English-ordinal exception handled correctly. Wired into both `PropertyDetail.tsx` (dashboard/owner view, "Ground Floor" / "3rd Floor") and `PropertyDetailClient.tsx` (public listing page).

### Location — Province/City are now cascading selects backed by real PH data

**What was found:** `location.city` and `location.province` were free-text `Input` fields — no canonical list backing them, so the same city could end up stored under any number of spelling/casing variants across listings (`"QC"` vs `"Quezon City"`, etc.), which would silently fragment anything that filters or groups by city later.

**What changed:** added `lynxbox-ph/src/data/philippineLocations.ts` — 82 provinces and 1,632 cities/municipalities (`PH_PROVINCES: string[]`, `PH_CITIES: { name, province }[]`, `getCitiesForProvince()`), sourced from PSGC (Philippine Standard Geographic Code) data via the `ph-locations` npm package and copied in as a static data file rather than kept as a runtime dependency — consistent with this repo's preference for self-contained data over small utility packages (verified the package's contents directly via `npm pack` before copying, no arbitrary/unverified data pulled in). `PropertyForm.tsx`'s Province/City fields became a cascading `Select` pair: City is disabled with a "Select a province first" placeholder until a Province is chosen, then lists only that province's cities/municipalities; changing Province clears whatever City was selected, since it may no longer be valid. An existing property whose stored city/province doesn't exactly match the canonical list (typos, legacy free-text data) still displays and stays selectable — added as an extra option rather than silently dropped or overwritten, same defensive pattern used elsewhere in this doc for not-yet-existing/mismatched data.

**Known data quirk:** a handful of municipality names in the source dataset carry minor punctuation differences from official spelling (e.g. `"Tawi Tawi"` rather than `"Tawi-Tawi"`, `"Hinoba An"` rather than `"Hinoba-an"`) — cosmetic only, not hand-corrected across all ~1,600 entries; worth fixing individually if a specific listing needs the exact official spelling.

## Property Number — human-friendly identifier

### What was found

Both the owner-facing (`PropertyDetail.tsx`) and public (`PropertyDetailClient.tsx`) detail pages showed the raw UUID as "Property ID" — including to anonymous site visitors, in a spot right next to the listing's other reference info. A GUID isn't something anyone would reference verbally (e.g. over a phone call about a listing), and it doesn't match this app's own precedent: Invoice already has a human-friendly `invoiceNumber` (`INV-<billingMonth>-<seq>`), generated by reading the existing count for that owner+month and using `count + 1`.

### What changed

- **`Property.propertyNumber: string`** (`api/src/models/property.ts`) — assigned once at creation, immutable afterward (protected the same way `id`/`ownerId`/`createdAt` already are in `updateProperty`'s field-stripping). Format: `LB-00000123` (8-digit zero-padded sequence).
- **Platform-wide atomic counter, not "count existing + 1".** Invoice's generation approach (list everything for that owner+month, take `length + 1`) is fine because it's scoped per-owner — but Property listings are public across every owner on the platform, so the numbers need to be globally unique, and re-listing-then-counting isn't safe against concurrent creates from different owners. `PropertyRepository.getNextPropertyNumber()` instead reuses the atomic-`ADD` counter pattern already established in `AccountRepository.incrementMonthlyInvoiceCount` — a single `UpdateCommand` with `ADD sequence :one` against one singleton row (`PK/SK: COUNTER#PROPERTY_NUMBER`), atomic without needing a transaction. Added `EntityType.COUNTER` to register this new kind of row (`api/src/lib/dynamodb.ts`).
- **Existing properties get backfilled, not lazily assigned on read.** `api/src/scripts/backfillPropertyNumbers.ts` (run via `npm run properties:backfill-numbers`, same shape as the existing `usage:backfill` script) scans for properties missing a `propertyNumber`, assigns them in `createdAt` order by drawing from the same counter new creates use, and is safe to re-run (`ConditionExpression: attribute_not_exists(propertyNumber)` skips anything already assigned). Chosen over lazy assignment-on-first-read specifically to avoid a "concurrent reads race to assign different numbers" class of bug.
- Both detail pages now show **"Property Number"**: `property.propertyNumber` (falling back to `property.id` if somehow absent). Naming settled on "Number" over "Code" to match the existing "Invoice Number" convention — "Code" reads more like something you'd type into a box (promo code, referral code), not a reference identifier for a specific record.

### Scope note — display-only, not a URL/routing change

This only replaces what's *shown*; the public URL (`/properties/detail?id=<uuid>` / `/properties/[id]`) still resolves by the raw UUID, same as before. Making the URL itself use `LB-00000123` would need a code→property lookup, which isn't free with this table's single-GSI design (GSI1 is already committed to owner-scoped queries) — the clean way would be a second lightweight pointer item per property (`PK: 'PROPERTY_NUMBER#<number>'` → `{ propertyId }`), not a new GSI. Deliberately left out of this round; worth doing later only if prettier/shareable URLs turn out to matter.

## Listing visibility enforcement — a real gap closed, plus a Renew action

### What was found

Tracing through "how does listing visibility duration actually work end to end" surfaced a real, pre-existing bug: three separate public endpoints only checked `property.status !== 'available'` and never checked expiry or the Payments plan's past-due suspension at all — `getPublicProperty` (the listing detail page itself), `getPublicPresignedViewUrl` (public image URLs), and `getPublicContactInfo` (the contact-reveal endpoint from this doc's scraping-protection section). So an expired or past-due-suspended listing correctly disappeared from browse/search results, but was still fully reachable — detail page, images, even contact info — by anyone with the direct/bookmarked link.

Separately: **the manual "renew an expired listing" mechanism (`PUT /api/properties/{id}` with `renew: true`) existed entirely on the backend with no UI anywhere to trigger it.** No button, no `renew` field even declared on the frontend's `PropertyUpdate` type. Every plan's listings — not just Free's, all three finite-duration tiers use the identical mechanism — would go dark after their window with literally no way for the owner to bring them back except calling the API directly.

### What changed

- All three endpoints above now also check `isListingCurrentlyVisible()` (exported from `propertyRepository.ts` rather than duplicating the expiry/suspension logic) — an expired or suspended listing now consistently 404s everywhere, not just in list/search. `getStaticListingImageUrl` was deliberately left alone — it's explicitly designed to skip DynamoDB entirely for embeddable widgets, so adding a lookup there would defeat its purpose.
- Added a **Renew action**: `DashboardPropertyList.tsx` (both card and table view) and `PropertyDetail.tsx` show a Renew button (`RepeatIcon`), calling `propertyService.updateProperty(id, { renew: true })`. Added `renew?: boolean` to the frontend `PropertyUpdate` type (was simply missing) and a shared `isPropertyExpired()` helper (`lynxbox-ph/src/lib/utils.ts`, mirrors the same check the backend already had).
- Added an **"Expired" badge** next to the status badge in both components, and `expiresAt`/`listingSuspended` to the frontend `Property` type (present in the wire payload all along, just never typed) — so an owner can actually see *why* a listing isn't showing up, not just notice it silently vanished.
- **Renew was originally gated on `isPropertyExpired(property.expiresAt)` — only appearing once a listing had already gone dark.** Since there's no other UI showing an owner *when* a listing expires, the button's own appearance was the sole signal, and the owner had no way to renew proactively. Changed to always show Renew whenever `property.status === 'available'` (renewing a draft/rented/sold/maintenance listing isn't meaningful — those go through Publish or a status change instead, which already computes a fresh `expiresAt`). Renewing early is safe: `renew: true` unconditionally sets `expiresAt = now + listingDurationDays` with no extra plan-cap check when the listing is already `'available'`, so there's no penalty for renewing before expiry — the only tradeoff is it resets from *now* rather than stacking onto the remaining time, so renewing a week early nets less than the full duration. Added a `formatExpiryDate()` helper (`lynxbox-ph/src/lib/utils.ts`) — "Expires Oct 5, 2026" / "Expired Oct 5, 2026" / "Never expires" (unlimited-duration plans) — shown next to Renew in all three places so an owner can see the date without waiting for the button state to change.

### A related, real bug found and fixed the same pass: editing an unlisted property

`PropertyForm.tsx`'s Property Status field is (was) `z.enum(['available', 'rented', 'sold', 'maintenance'])`, with a `<Select>` offering exactly those four options — but `reconcilePropertyListingsForPlan()` (see docs/Pricing-Strategy-Plan.md) can set a fifth value, `'unlisted'`, that was never in the enum or the dropdown at all. Since it's a plain native `<select>`, opening the edit form for an unlisted property silently fell back to displaying "Available" (the first option) — and saving without deliberately touching Status would submit `status: 'available'`, silently undoing the plan-limit enforcement the moment the owner edited anything else.

Fixed by widening `PropertyStatus`/the zod enum to include `'unlisted'`, but rendering `<option value="unlisted">` **only when the property's current status already is `'unlisted'`** — so it displays correctly and can be freely switched *away from* (that's the actual re-listing mechanism the billing page's own copy already promises: "you can choose which to re-list"), but is never offered as something to manually switch *into*. An explanatory line appears next to the dropdown when this applies, telling the owner why and what to do.

## Draft status

### What was found

A brand-new listing had no way to exist privately — the moment `POST /api/properties` succeeded, it was `status: 'available'` (hardcoded, ignoring whatever status the caller sent), immediately public, and immediately counting against the plan's `maxProperties` cap. There was no way to prepare a listing — write the description, pick photos — without it going live and consuming a slot the instant "Create" was pressed. This was flagged and deliberately deferred earlier in the session (see `docs/Pricing-Strategy-Plan.md`'s implementation notes) pending a decision on whether drafts should count against the cap — that question resolved itself for free once the active-listing definition was narrowed to `status === 'available' && not expired` (see this doc's own history and the Pricing plan doc): a draft simply never matches `'available'`, so it's automatically excluded with no extra enforcement code needed.

### What changed

- **`'draft'` is a real, owner-selectable `PropertyStatus`** — unlike `'unlisted'` (system-only), it's a normal, always-visible option in `PropertyForm.tsx`'s Status dropdown. New listings still default to `'available'` unless the owner explicitly picks Draft (a smaller, less disruptive change than flipping the default — easy to revisit if immediate-publish turns out to surprise people less than expected).
- **`createProperty` now actually respects a caller-supplied status** (`CREATABLE_STATUSES = ['available', 'rented', 'sold', 'maintenance', 'draft']`, defaulting to `'available'` when omitted or invalid) instead of hardcoding `'available'` regardless of input — this hardcoding is *why* there was never a way to create anything but a live listing before now.
- **The visibility-duration clock only starts once a listing is actually live.** `expiresAt` used to be computed unconditionally at creation from the plan's `listingDurationDays`, regardless of status — meaning a draft created today and published weeks later could already be "expired" the moment it went live. Now `expiresAt` stays `null` for anything other than `'available'`, and gets computed fresh (same formula `renew` uses) at the exact moment a listing *transitions into* `'available'` — whether that's the initial create, or a later publish.
- **Publishing a draft (or un-marking rented/sold/maintenance back to available) re-runs the same plan-cap check `createProperty` does.** Without this, drafts would've been a loophole: create unlimited drafts (they don't count), then publish them one at a time past the plan's actual limit, since `updateProperty` never checked `maxProperties` at all before now. `PropertyHandler.updateProperty` detects this exact transition (`updates.status === 'available' && property.status !== 'available'`) and applies the identical cap check.
- **Closed a related, adjacent gap while in this exact validation code**: nothing previously stopped a direct API call from setting `status: 'unlisted'` via a normal update (the frontend dropdown already prevented it, but the backend didn't enforce it). `updateProperty` now rejects `status: 'unlisted'` outright — the only legitimate path to that value is `reconcilePropertyListingsForPlan` calling `PropertyRepository.update()` directly, which bypasses this handler entirely, so the guard doesn't break anything real.
- **A "Publish" quick action** (`CheckIcon`, purple) appears next to "Renew" in `DashboardPropertyList.tsx` (both views) and `PropertyDetail.tsx` whenever `status === 'draft'`, calling `updateProperty(id, { status: 'available' })`. A distinct purple badge (`statusBadgeColor()` helper) distinguishes "not yet published" from the orange used for rented/sold/maintenance ("was published, now off-market") — a deliberately different color since the two mean different things to an owner scanning their listing list.

## Property CSV import

### What was found

Tenant already has a working CSV bulk-import (`TenantCsvUpload.tsx`, documented in `CLAUDE.md`'s Frontend section) — property had nothing equivalent. The one genuine wrinkle, flagged up front rather than discovered mid-build: **images can't travel through a CSV.** The direct-to-S3 upload flow (see this doc's "Image upload" section) needs real browser `File` objects for the presigned-PUT step — there's no reasonable way to carry binary image data through a spreadsheet cell.

### What changed

- **`lynxbox-ph/src/features/properties/components/PropertyCsvUpload.tsx`** (new) — mirrors `TenantCsvUpload.tsx`'s pattern exactly: module-level `CSV_HEADERS`/`EXAMPLE_ROW`, the same hand-rolled `parseCSV`, a `validateRow()` producing `{ rowNum, data, errors, payload }`, template download via Blob, sequential (not `Promise.all`) import loop with a progress bar, toast summary at the end. Wired in as an "Import CSV" button next to "Add Property" in `DashboardPropertyList.tsx`, reusing its existing `properties` state and `loadProperties()`.
- **Images resolved by defaulting imported listings to `status: 'draft'`** rather than inventing an image-URL-fetch mechanism (which would mean the backend downloading arbitrary external URLs — a meaningfully larger, riskier feature, not attempted). A row can still set `status` explicitly if the owner wants it to go live immediately without photos. Owners add photos afterward via each listing's normal edit page, then publish.
- **Create-vs-update matching uses `propertyNumber`** (e.g. `LB-00000123`) as the identifier — same role `lesseeNo`/`tenantCode` plays for Tenant's import. On update, `images` is deliberately left out of the payload entirely (not set to `[]`) so a CSV-driven update can never wipe a listing's existing photos — the same "omit rather than send an empty value" caution `updateProperty`'s own image-handling already relies on elsewhere.
- **City/province are validated against the real PH province/city data** (`philippineLocations.ts`) rather than accepted as free text, case-insensitively matched and normalized to the canonical casing — so a bulk import can't reintroduce the spelling-variant fragmentation (`"QC"` vs `"Quezon City"`) the manual form's cascading dropdowns were built to prevent. `'unlisted'` is rejected as a CSV status value, same "system-only" rule the manual form enforces.

### Follow-up fixes after live testing

- **Template column misalignment, a real bug not just a bad example.** `downloadTemplate()` built the CSV via a naive `EXAMPLE_ROW.join(',')` — the example description ("...unit, ready for occupancy.") had a comma of its own, which silently added an extra column with no quoting to stop it. Any real title/description/address containing a comma would do the same. Fixed with a proper `csvField()`/`toCsvRow()` helper that quotes a field (RFC 4180 style: wrap in `"..."`, double up embedded quotes) whenever it contains a comma, quote, or newline.
- **The `status` column was removed, then restored** — first removed on the reasoning that every import defaults to draft anyway, then added back so a row can still explicitly request `status: available` (e.g. re-importing/updating already-photographed listings). Restoring it surfaced a real question: **could a bulk "10 new listings, all `available`" import blow past the plan's active-listing cap with no warning until scattered per-row failures during the import itself?** Fixed by fetching `billingService.getUsage()` (real `limits.maxProperties` + current `usage.properties`) once when the file is parsed, then running a second validation pass (`flagOverCapRows()`) that flags — in the same preview table, before any API call — whichever rows would push the count over the limit, same "counts against the cap" definition as the backend (`status === 'available'`, and for an update row, only if it's *newly* becoming available).
- **A related, latent bug caught while restoring the status column**: an update row used to apply `status` unconditionally (defaulting to `'draft'` when blank) — meaning a CSV row that only meant to update a listing's *price* would have silently reverted an already-published listing back to draft the moment its status column was left empty. Fixed so an update row only touches `status` when the column is explicitly set; left blank, the existing listing's status is never touched.

## Property CSV import — bundled image ZIP

### What was found

The CSV import above deliberately left photos out — every imported row landed as `'draft'` with `images: []`, and an owner had to add photos one listing at a time afterward. Scoped and built as a way to bring photos along in the same bulk import, without ever routing raw image bytes through anything but the upload pipeline that already existed.

### What changed

- **CSV gains 10 image-reference columns**: `defaultImage`, `image2`, `image3`, ... `image10` (`IMAGE_COLUMNS` in `PropertyCsvUpload.tsx`). Each cell holds a filename (e.g. `unit-3-living-room.jpg`) that must exist in a companion ZIP — not the image data itself, just a pointer to it. `defaultImage` (if filled) always becomes `images[0]`/`defaultImageIndex: 0`; the rest follow column order.
- **A third upload step, "Step 3 — (Optional) Upload a ZIP of images"**, parsed client-side the moment it's selected using **JSZip** (new dependency, see below). `buildZipIndex()` walks every non-directory entry and indexes it by lowercased basename (folder path ignored) — a basename that appears more than once anywhere in the ZIP is stored as `null`, meaning "ambiguous," so every row referencing it gets a clear error rather than one copy being silently picked over another.
- **Matching and validation happen entirely client-side, before any network call.** `resolveRowImages()` (called from `validateRow()`) checks each filled image column against the ZIP index: not found → row error naming the exact filename; ambiguous → row error explaining the duplicate; a column filled in with no ZIP uploaded at all → its own explicit error. All of this lands in the same preview table and error-details list the CSV importer already had, so a mismatch is caught and shown before a single property is created.
- **The preview table's new "Images" column** shows "N matched" (green) per row, or "mismatch" (red) when image columns were filled in but didn't all resolve — the row's full reason still shows in the error-details list below the table.
- **Unmatched ZIP entries surface as a non-blocking info banner** ("N files in the ZIP aren't referenced by any row: ...") — `findUnusedZipEntries()` diffs the ZIP's basenames against every row's filled-in image columns. Doesn't block import; it's there to catch a likely typo.
- **Import reuses the existing per-image pipeline untouched.** For each valid row with resolved images, `handleImport()`'s existing sequential loop pulls each matched entry out of the ZIP as a `Blob` (`entry.async('blob')`), wraps it in a `File` (MIME type guessed from the extension via `guessImageMimeType()`, since a ZIP entry carries no `Content-Type`), and calls the exact same `propertyService.uploadPropertyImage(propertyId, file)` that `PropertyForm.tsx` already uses — presigned upload-url → raw `PUT` → `/images/confirm` (watermark/resize happens server-side same as always). No new upload endpoint, no server-side unzip, no temp S3 folder to clean up. `propertyId` for a create row is the same client-generated `crypto.randomUUID()` `validateRow()` already produces (same pattern as `PropertyForm.tsx`'s `activePropertyId`), so images upload before the property record exists, same as the manual form's flow.
- **Payload construction moved later for image-bearing rows.** `validateRow()` only sets `images: []` upfront when a create row has *no* resolved images — otherwise `images`/`defaultImageIndex` are filled in inside `handleImport()`'s loop, right before the create/update call, once every referenced file for that row has actually finished uploading.
- **Update rows replace images wholesale when any image column is filled in** — not a merge/append. An update row that leaves every image column blank keeps behaving exactly as before: `images` omitted from the payload entirely, existing photos untouched. Documented in the template's Step 1 help text.
- **All-or-nothing per row.** If any one of a row's referenced images fails to upload, that row's property is not created/updated at all — the per-row `try/catch` `handleImport()` already had for its `failCount`/`successCount` bookkeeping naturally covers this, since the image uploads happen inside the same try block as the create/update call.
- **300MB client-side ZIP size cap** (`MAX_ZIP_SIZE_BYTES`), checked before `JSZip.loadAsync()` even runs — everything happens in browser memory (no server-side unzip), so this guards against the tab hanging/crashing on an unreasonably large file.

### New dependency

**JSZip**, added to `lynxbox-ph/package.json` — a deliberate exception to the repo's general preference for avoiding small utility-package dependencies (see `philippineLocations.ts`'s "copied in as static data, not kept as a dependency" convention in this same doc): ZIP decompression isn't something to hand-roll or vendor as static data, unlike a lookup table.

### Deferred, not built

- A per-image "uploading image 3/10..." status line during a many-photo row's processing — the existing per-row (not per-image) progress bar granularity was kept as-is.
- Reordering images after matching, a drag-and-drop re-upload UI for fixing a single mismatched row without re-uploading the whole ZIP, and resuming a partially-completed import (a failed row today just needs its CSV row and ZIP re-submitted).

### Restricted to Growth/Business

The whole bulk-import feature (plain CSV and the ZIP-bundled-photos extension both) is gated to Growth/Business via `PLAN_LIMITS.csvImportEnabled` — see docs/Pricing-Strategy-Plan.md's Implementation notes #19 for the full reasoning, including why this is a frontend-only gate (`DashboardPropertyList.tsx`'s "Import CSV" button) rather than something enforced in the API: there's no dedicated bulk-import endpoint, since the importer just calls the same `createProperty`/`updateProperty` a manual "Add Property" click already uses.

## Property type taxonomy: dropped `commercial`, added `retail`/`warehouse`/`industrial`

### What was found

Discussed live with the user rather than found as a bug: the original three types (`office`/`commercial`/`land`) lumped every non-office, non-land listing under one catch-all `commercial`, losing a distinction (retail storefront vs. warehouse vs. industrial space) useful for search filtering. Investigating turned up real prior-art for a richer taxonomy already sitting dead in the codebase: `PropertyDetailClient.tsx`'s `getPropertyTypeColor()` mapped colors for `'office-space'`, `'retail-space'`, `'warehouse'`, `'co-working'`, `'executive-suite'`, `'home-office'` — none of which matched the actual 3-value enum, so every public listing badge silently rendered gray (the fallback) — a leftover from some earlier, richer type list that was trimmed down without this map being updated.

### What changed

Final list, after narrowing down from that recovered set (dropped `co-working`/`executive-suite`/`home-office` as not fitting a B2B commercial-landlord platform): **`office`, `retail`, `warehouse`, `industrial`, `land`**. `type` is stored as a plain string on the backend (no server-side enum), so this was purely a frontend migration, but the actual value list turned out to be hardcoded independently in far more places than expected — an Explore-agent audit found it duplicated in **9 files**: the two separate `PropertyType` declarations (`services/propertyService.ts` and a non-re-exported duplicate in `features/properties/types.ts`), `PropertyForm.tsx`'s zod enum *and* its JSX `<option>` list (two independent copies in the same file), `DashboardPropertyList.tsx`'s and `app/properties/page.tsx`'s own filter-checkbox arrays, an orphaned/unused `PropertyList.tsx`'s inline options, and `PropertyCsvUpload.tsx`'s validation list. Cleaned up both stale color-map functions in the same pass — `PropertyDetailClient.tsx`'s dead one above, and `PropertyCard.tsx`'s `getTypeColor()`, which mixed in leftover `apartment`/`house`/`condo` keys that were never part of any real `PropertyType` at all.

## Real bugs found through live testing — image pipeline

Several real, previously-invisible bugs surfaced only once Draft status and real multi-image uploads were actually exercised end-to-end. None were caught by `tsc`/build — all found by testing the running app and tracing the actual failure.

- **`SecureImage.tsx` always routed through the *public*, no-auth image endpoint, regardless of context.** `const usePublic = usePublicEndpoint === true || usePublicEndpoint === undefined || propertyId` — since `propertyId` is virtually always a non-empty string, this was unconditionally `true`. Every dashboard/owner view (`PropertyForm.tsx`'s photo previews, `DashboardPropertyList.tsx`'s thumbnails, `ImageGallery.tsx`, etc.) silently called the public endpoint instead of the authenticated one. Invisible before Draft existed, because every property used to become `status: 'available'` the instant it was created — the public endpoint's `status === 'available'` gate never had anything to block. The moment Draft existed, an owner's own preview of their own unpublished photos started 403ing. Fixed: `usePublic` is now only `true` when the prop explicitly says so (only `PropertyDetailClient.tsx`, the real public page, does). Also removed a silent fallback to a hardcoded, unsigned direct-S3 URL on API failure — the bucket isn't public, so that fallback could only ever also fail, and was masking the real error rather than fixing anything.
- **`getPresignedViewUrl` (the authenticated image-view endpoint) had zero ownership check** — any logged-in user could have viewed any other account's property images just by knowing an id + key. Dormant/unexploited only because the bug above meant this endpoint was never actually called by the frontend; fixed *before* flipping that routing over, by adding the same `resolveActor` + `property.ownerId === actor.accountId` check every other handler in this file already has.
- **`PropertyRepository.getNextPropertyNumber()`'s `UpdateExpression` used `sequence` as a bare, unaliased attribute name — `sequence` is a reserved word in DynamoDB's expression grammar.** Every property creation failed with a `ValidationException` until this was found (via the actual error, once surfaced — see below) and fixed by aliasing it through `ExpressionAttributeNames` (`#sequence`). `AccountRepository`'s otherwise-identical counter pattern uses `invoiceCount`, which happens not to collide with anything reserved, which is why that one silently worked and this one didn't.
- **Two handlers swallowed the real error and returned a generic message** — `confirmImageUpload` (properties) and `PropertyStatusUpdater.tsx`'s status-change handler both did the equivalent of `catch (error) { toast('Something failed, try again') }`, discarding whatever specific, user-actionable reason the backend actually gave (a validation message, a plan-cap rejection, etc.). This is exactly what masked the reserved-word bug above from being diagnosable from the browser alone — the browser only ever showed "Internal Server Error" until the message was fixed to surface `error.message`. Both now do.
- **`ImageProcessingService.validateImage()`'s 5000×5000 max-dimension check was rejected real, normal photos.** Modern phone cameras routinely exceed 5000px on the long edge (a 48MP shot can be 8000×6000+). Since every image gets resized down to 1200×900 immediately after this check anyway (`processForPropertyUpload`), the upper bound served no purpose — removed it, keeping only the 100×100 minimum (a real quality floor, unrelated to memory/rejection concerns).
- **Image size cap raised from 5MB to 10MB** — in all three places it's enforced: `S3Service.validateImageFile` (backend), `lib/utils.ts`'s `validateImageFile` (frontend pre-check), and `PropertyForm.tsx`'s helper text.
- **Verified the resize/watermark pipeline is genuinely working** — not just by code review, but by pulling real uploaded objects directly out of S3 and inspecting them: every sampled image (across 4 different properties) was correctly stored as 1200×900 JPEG. One cosmetic-only oddity noted: the S3 key's file extension reflects whatever the browser originally uploaded (e.g. `.png`), even though the re-encoded content is always JPEG — harmless, since browsers go by the `Content-Type` header, not the URL extension.
- **Considered and declined changing the crop behavior.** `fit: 'cover'` (crop-to-fill) can visibly cut off content on images whose source aspect ratio isn't close to 4:3 (demonstrated with an atypical test upload — a portrait tourism-collage graphic — where a caption got cropped off). Presented the tradeoff (switch to `fit: 'contain'`/letterbox vs. keep cropping vs. drop the forced aspect ratio entirely); decided to leave it as-is, since real property photos are typically already close to landscape/4:3 and this mainly affects atypical, non-representative source images.
- **`PropertyCard.tsx` (the public `/properties` browse page's card, the only place it's used) never passed `usePublicEndpoint` to `SecureImage` at all** — the exact opposite direction of the routing bug above. A logged-in viewer browsing the public marketplace only saw thumbnails for listings *they themselves* own; every other owner's listing showed "Image unavailable" (found via a real screenshot: 3 of 4 cards loaded, the one not owned by the logged-in tester didn't), because the default (no prop passed) routes through the authenticated, ownership-gated endpoint. Fixed by passing `usePublicEndpoint` on this card, same as `PropertyDetailClient.tsx` — this is the second and last real caller of `SecureImage` on the public site.

## `PropertyStatusUpdater.tsx` fixes

The "Quick Status Update" dropdown+button shown in `DashboardPropertyList.tsx`'s card view (a separate, pre-existing component, not something built this session) had its own version of the same class of bug already found and fixed in `PropertyForm.tsx`'s Status field:

- **`statusOptions` didn't include `'draft'` at all.** Since this is a *controlled* `<Select value={status}>` (React state, not a native uncontrolled select), the internal state correctly held `'draft'` — but with no matching `<option>`, the dropdown visually fell back to showing "Available", even though the Update button was correctly disabled (internally, `status === property.status`). Fixed by adding `'draft'` as a normal, always-available option — and, once fixed, this made the separate "Publish" button added earlier **redundant** in card view specifically (selecting Available + clicking Update now does exactly the same thing, through the same backend endpoint and cap-check). Removed the card-view Publish button; **kept it in table view and `PropertyDetail.tsx`**, since neither has an equivalent quick-status control.
- **`'unlisted'` handled the same conditional-only way `PropertyForm.tsx` already does** — added as an option only when a property's current status already is `'unlisted'`, never offered as something to manually switch into.
- **Error handling discarded the real backend message** — same fix as `confirmImageUpload` above, now shows `error.message` instead of a hardcoded generic string. Directly relevant here since this control can now legitimately fail with a specific, actionable reason (hitting the plan's active-listing cap on publish) that the old generic message would have hidden.

## Other changes made this session

- **Description character counter** — `PropertyForm.tsx`'s Description field now shows a live `n/1000` counter (red past the limit) next to the existing validation error, and the `Textarea` got `maxLength={1000}` so it can't be typed past the zod schema's existing `.max(1000, ...)` limit in the first place. Purely a UX addition, no backend change (the 1000-char limit already existed and was already enforced by validation — this just makes it visible while typing).
- **Description line breaks weren't rendering on the public page.** `PropertyDetail.tsx` (dashboard/owner view) already had `whiteSpace="pre-wrap"` on its description `<Text>`; `PropertyDetailClient.tsx` (the public page) didn't, so a description typed with paragraphs/bullet lines rendered as one run-on block. Added the same `whiteSpace="pre-wrap"` there — no editor needed for this; a rich-text editor would be a separate, much bigger addition (new dependency, and now storing/rendering user-authored HTML needs sanitizing against XSS) only worth it if actual inline formatting (bold/italic) is wanted beyond preserved line breaks.
- **Tooltips added to every icon-only button** in `DashboardPropertyList.tsx` (the view-mode toggle, and all table-view row actions: View/Edit/Renew/Publish/Delete) — previously icon-only with no hover label at all.
- **Card/Table view selection now persists** (`localStorage`, same pattern already used for the search filters in this same component) instead of resetting to Card view on every visit.
- **Table view no longer shows the description snippet** under each property's title — title + type badge only, keeping the row compact.
- Removed the "Draft listings are only visible to you..." helper text from `PropertyForm.tsx`'s Status field — a UX simplification, not a bug fix.
- **Dashboard's "Active Listings" stat card repeated its own number** — the big stat number (`3`) was immediately repeated at the start of the helper text below it ("3 of 15 used"), unlike the three other stat cards on the same page, which all just say "of N allowed" without echoing the number. Reworded to match (`of 15 allowed`).
- **`PropertyCard.tsx` (public browse page) buttons misaligned row-to-row whenever a card had a short title or no description** — since each card's content stacked from the top with no shared height, a card with less content above the button row ended up with its buttons sitting higher than its neighbors in the same grid row. Fixed by making the `Card`/`CardBody`/`Stack` stretch to fill the row height (`h="full"`, `flex="1"`) and adding a `Spacer` before the price/button block, so that block now anchors to the bottom of every card regardless of what's above it. Also reserved a fixed `minH` on the title so a one-line title doesn't shrink the block either.
- **Removed the description entirely from `PropertyCard.tsx`** (public browse page) per a direct request to simplify the card — title, location, features, price, buttons, "Listed by" only. The dashboard's own card/table views (`DashboardPropertyList.tsx`) are unaffected; only the public-facing card changed.
